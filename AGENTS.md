# AGENTS.md

**laplacekit**: an extensible, modern Laplace-approximation library for PyTorch,
built on a plugin system. Alpha (0.1a): the API changes without deprecation.

## Where things are

- Design (authoritative intent), decision log, milestone plans, and execution
  ledgers live **outside** this repo, in the author's private planning
  directory. Read the design doc and the current milestone plan before changing
  behavior. Never put design notes, plans, or local paths in the repo.
- `src/laplacekit/core/`: the contracts and machinery (interfaces, operators,
  posteriors, fitting orchestration, probe, tuning). `laplacekit.core` exports the
  public core API.
- `src/laplacekit/*.py`: built-in plugins and the front door (`curvature`,
  `likelihoods`, `priors`, `predictive`, `subsets`, `objectives`, `data`,
  `front`, ...). They are written exactly like third-party plugins.
- `plugins/`: separate plugin packages in the uv workspace, depending only on
  the public API. First-party: `laplacekit-transformers`, `laplacekit-diffusers`,
  `laplacekit-subnet` (subnetwork selection), `laplacekit-heteroscedastic`
  (heteroscedastic regression), `laplacekit-reward` (reward models on preference
  pairs), `laplacekit-gp` (GP methods for function-space Laplace) and
  `laplacekit-marglik` (marginal-likelihood training). They install through the
  extras `laplacekit[transformers]`, `laplacekit[diffusers]`, `laplacekit[subnet]`,
  `laplacekit[heteroscedastic]`, `laplacekit[reward]`, `laplacekit[gp]` and
  `laplacekit[marglik]`, and code reaches them as the lazy aliases
  `lk.transformers`, `lk.diffusers`, `lk.subnet`, `lk.heteroscedastic`,
  `lk.reward`, `lk.gp` and `lk.marglik`.
  Every plugin registers an `lk.Plugin` under the `laplacekit.plugins`
  entry-point group. A plugin's `__init__.py` holds its docstring, the
  re-exports (`__all__`), `health` and the `plugin` record; the code sits in
  modules named by topic (a leading `_` when a module holds only helpers).
- The docs' example plugin, `laplacekit-example` (`last_layers(n)`), lives in
  its own repository, `laplacekit/laplacekit-plugin-example`, a GitHub template
  for new plugins. It stays one file. The docs group installs it from git, and
  "Your first plugin" shows its `__init__.py`; the test and `pyproject.toml`
  excerpts on that page are copies, so update them when the template changes.
- `docs/`: Quarto site. `docs/quickstart/*.py`, `docs/examples/*.py` (In depth)
  and `docs/plugins/*.py` are percent-format scripts that double as UX tests
  (`make docs-full` runs every one; `make docs` reuses frozen outputs). On
  every push to `main`, `.github/workflows/docs.yml` renders the committed
  `docs/_freeze/` (nothing executes in CI) and deploys it to Cloudflare Pages,
  so commit the freeze with every docs change; `docs/plugins/*.qmd` are static.
  `docs/reference/` is generated by quartodoc.
- `tests/typing/`: scenarios type-checked by `ty`; `test_mistakes.py` holds
  deliberate errors, each marked `# EXPECTED ERROR`.

## Commands

Always go through `uv` (never global Python). The machine is CPU only.

```bash
make sync        # uv sync --group docs
make check       # ruff check + format check, ty, import-linter, pytest (the CI gate)
make test TESTS=tests/test_front.py ARGS="-k tune"
make fix         # ruff fixes, then format
make docs        # quartodoc reference + Quarto render into docs/_site; frozen
                 # pages (docs/_freeze/) re-execute only when their source changed
make docs-full   # clear docs/_freeze/ and re-execute every page (milestone ends)
make docs-serve  # live preview at localhost:4200 (PORT=... to change)
```

Quarto comes from the `quarto-cli` package in the docs group; no system install.

## Rules

- **Import boundary.** Built-ins and plugins import only `laplacekit.core` (the
  package) or `laplacekit`, never `laplacekit.core.<submodule>`; import-linter
  enforces it. Only `core/_pytree.py` may touch `torch.utils._pytree`. Only the
  Curvlinops adapter may import `curvlinops` (and read its private attributes,
  pinned to `curvlinops-for-pytorch==3.0.1`, with a guard test). Only
  `core/_functorch.py` reads torch's private functorch state
  (`torch._C._functorch`, and `torch._C._DisableFuncTorch`, which
  `core/_seed.py` uses through it to draw a seed under `vmap`), each read with a
  guard test. Built-ins and plugins import no private names from
  `laplacekit.core`: they get generators from `spawn_generator` and
  `generator_for_batch`.
- **Models through autograd only.** Never inspect a model's structure to decide
  behavior. Methods declare `Requirements`; the probe records `Capabilities`;
  a mismatch raises `CapabilityError` before any data is consumed.
- **No silent fallbacks, no string dispatch.** Unsupported requests raise
  `CapabilityError` or `StructureError` naming what is missing. Options are typed
  objects or `Literal`s. Dispatch with `isinstance` on (runtime-checkable)
  protocols, never `hasattr`/`getattr` on names.
- **Immutable objects.** Components are `@pytree` frozen dataclasses (`static()`
  for non-tensor fields); steps return new objects (`copy.replace`).
- **Curvature conventions.** Statistics are monoids (`init` is the identity, `+`
  combines; test `fold(a ++ b) == fold(a) + fold(b)`). `finalize` returns
  per-example averages; posteriors multiply by `n_data` (the effective data size).
  Multi-pass methods are `Staged` chains built with `chain(...)`.
- **D8.** By-hand fits stay differentiable with respect to the passed
  params; only the front door detaches and runs its fit loop under `no_grad`.
- **Typing.** `ty` must be clean on `src`. New public names are typed; prefer
  fixing types over suppressions, and justify any `# ty: ignore[...]`.
- **Tests first.** Every change comes with tests that fail before it. Compare
  against independent references (dense matrices, `torch.func`, laplace-torch
  numbers), not against the code's own helpers.

## Style

- Code: generous blank lines between logical blocks inside functions (after the
  docstring, between setup / computation / return, around loops and if-blocks).
  Dense functions get sent back.
- Docstrings and comments: short and plain. No marketing words. The one
  exception is the tagline, the author's wording: "modern" there means
  `torch.func`, Curvlinops and typed immutable pytrees.
- Example pages (`docs/examples/`): tutorial style, in the author's voice (his
  last-layer Laplace notebooks and blog). "We", the idea and its math first (in
  LaTeX), then the code.
- Quickstart (`docs/quickstart/`) and Plugins (`docs/plugins/`) pages: the
  author's voice too, but code first and short; math only in a collapsed
  "The math" callout (Quickstart) or after the smallest working example
  (Plugins).
- API reference, docstrings, and README: impersonal (no first person), direct,
  short sentences.
- All prose: GitHub alerts (README) or Quarto callouts (docs) for notes; the
  `---` dash sparingly. The name is **laplacekit** in prose: write
  `**laplacekit**` in the docs (`docs/brand.lua` sets it like the wordmark) and
  `<code><b>laplacekit</b></code>` in the README. Code imports it as
  `import laplacekit as lk`. Other libraries in monospace, linked in table
  headers.

## Git

- Work on `main` unless told otherwise. Code commits are fine.
- **Never commit README or docs changes without the author's approval.** Leave
  them in the working tree and summarize them.
- Push with SSH (`origin` is `git@github.com:laplacekit/laplacekit.git`), only when
  asked or at the end of a reviewed milestone.
